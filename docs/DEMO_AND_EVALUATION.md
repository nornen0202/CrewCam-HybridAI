# Shot list and evaluation

Use a repeatable, non-personal scene for cloud runs. For example, arrange a cake prop, two cups and a candle on a table. One subject remains identifiable when the closer camera reframes. The two originals and the screen recordings are different assets. Store originals privately by run and camera. Capture separate English screen footage from the exact tested build.

| Time | Picture and action | On-screen evidence |
| --- | --- | --- |
| 0–15 s | Two actual duplicate views side by side before the event. Show what the framing misses. | Source and scene type |
| 15–70 s | Pair the two phones, choose the subject, show the suggestion and physically adjust one camera. | Real model names, initial views, operator acceptance, then fresh verification from this run |
| 70–105 s | Demonstrate a local check with internet unavailable; show a consented cloud result. Display the source on both. | Keep forced cloud and automatic fallback clearly labelled, show measured waiting time for any time-compressed edit |
| 105–145 s | Play the two finalized originals side by side and compare with the verbal-role baseline. | Same-run filenames, independently labelled framing, full denominator |
| 145–165 s | Show how to install, what was built during the event and which phones were tested. | Tested build and access links |

Start each comparison trial on the same marked positions with the same event duration. Rotate the order of the unassisted, verbal assignment and CrewCam conditions across blocks. Use comparable operators, duration, lens options and lighting. Record a take even when setup or inference fails. Score both target views as retained only when reviewers can identify both in the recorded source files during the marked event. Have a reviewer score files without the condition label where practical. Report numerator/denominator and time per condition; a small trial supports a descriptive result.

For every take record run ID, app SHA-256, exact phone model/OS, product transport, controlling method, scene origin, route selections, actual sources, frame IDs, acceptance, physical adjustment, fresh verdict, original file hashes/durations, observer score and reason for failure. Verify file durations and fully decode both streams. Annotate a UI recording used for editing. Keep the old Gemma video as historical evidence.

A judge should be able to inspect three things directly: the code that chooses each permissible route; a receipt from the SDK on real hardware; and a saved pair whose framing changed in the demonstrated take. Record the unmeasured metrics as pending until each trial is collected.
